## 2026-08-08
### Performance (follow-up, session 6)
- **Root cause found for session 5's "severe LCP regression": a stuck site crawler, not WebP itself.** Investigation ruled out hero-image corruption (byte-identical markup with WebP on/off) and found the actual bug: the LiteSpeed "Guest - WebP" crawler — which warms the page cache and triggers QUIC.cloud's Critical CSS generation as it visits each URL — had silently stalled (`Ended reason: stopped_reset`, 0 of 50 URLs successfully crawled), almost certainly a WP-Cron reliability issue. This means Critical CSS regeneration hadn't been reliably running in the background since session 4's CSS Combine experiment, explaining the erratic, inconsistent Performance scores seen all session regardless of which setting was being tested. Manually triggered the crawler — it completed successfully (47/50 crawled). Also caught and fixed a cache-verification bug in the testing method itself: "purge, warm with a few curl requests, trust `x-qc-cache: hit`" can report a stale response as fresh (a purge-propagation race) — now verifies actual response content, not just the cache-status header.
- **Re-tested WebP against a properly-verified (though still mid-convergence) cache state**: real regression was more moderate than first measured — LCP 9.2s / Performance 56 (vs. the initial, likely cache-race-corrupted reading of 20+ seconds / effectively unusable). LCP breakdown showed a 2.57s "resource load delay" on the preloaded hero image, consistent with render-blocking CSS costs that were elevated because Critical CSS convergence was disrupted by the stuck crawler, not a WebP-specific defect.
- **Reverted WebP back off**, purged and warmed cache, confirmed a clean and *improved* baseline: Performance mobile 62 / desktop 86 (up from 61/85), Accessibility 97/97 ✅, Best Practices 100/100 ✅, SEO 100/100 ✅ — better than before, likely from fixing the stuck crawler alone.
- **Updated conclusion**: WebP delivery is not confirmed unsafe — the earlier verdict was measured against a broken CCSS pipeline. Recommended next step: confirm the crawler keeps completing automatically on its own 10-minute schedule (check for `Ended reason: end`, not `stopped_reset`) and let the freshly-triggered CCSS queue (83 requests) fully converge over real time before retrying WebP. See [`docs/2026-08-08-performance-follow-up.md`](docs/2026-08-08-performance-follow-up.md).
