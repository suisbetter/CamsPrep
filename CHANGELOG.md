### Performance (follow-up, session 5)
- **Both known Imagify WebP/JS conflicts genuinely fixed** — added a WPCode snippet using `IntersectionObserver` to patch Swiper's lazy-load so it correctly reveals `<picture><source>` elements (Imagify's rewrite), on top of session 4's LiteSpeed-lazy-load fix. Verified via real Swiper API navigation (not just page load): course-bundle cards, client-logos carousel, and testimonials carousel all render correctly with WebP, no broken images, no new console errors.
- **New, more severe regression found: Lighthouse-measured LCP blew up to 20+ seconds with WebP delivery live** — reproducible even on a warmed cache (confirmed via `x-qc-cache: hit`) and with the JS snippet simplified to remove a suspect `MutationObserver` (LCP stayed at 20.5s either way, ruling that out as the cause). Real fast browsing looked and felt fine; only Lighthouse's throttled-CPU trace showed the problem. **Reverted Imagify WebP delivery back off immediately** given the severity — confirmed clean recovery to baseline (mobile 61 / desktop 85) after revert. Root cause not identified this session; likely candidates for a future investigation: DOM size increase from `<picture><source>` wrapping (94 elements) interacting badly with Lighthouse's CPU throttling, or a slow per-request PHP rewrite. WPCode snippet (10920) left in place but inactive, ready for reuse.

### Performance (follow-up, session 4)
- **LiteSpeed's own JS-based lazy-load disabled** — redundant with images' native `loading="lazy"` attribute, and was the root cause blocking Imagify's WebP `<picture>` delivery from rendering correctly. **Kept live** (safe, zero visual change).
- **Imagify WebP delivery retried, hit a second conflict, reverted again** — fixing the LiteSpeed lazy-load conflict let the course-bundle cards render correctly, but surfaced a second, independent conflict: the Swiper.js client-logos carousel doesn't support `<picture>`-wrapped lazy images, so logos went to broken-image icons. Given two distinct conflicts found back-to-back, reverted WebP delivery off pending a full site-wide carousel/gallery audit rather than whack-a-moling individual widgets in production.
- **CSS Combine + Generate UCSS attempted, reverted** — UCSS turned out to require Combine to function. Re-enabling Combine invalidated all previously-generated Critical CSS and caused a temporary Performance score drop to 49 while it regenerated (a multi-hour process). Reverted both back off and purged stale CCSS/UCSS files via Toolbox to force clean regeneration matching the reverted config. Architecturally the right next step, but needs a session with a multi-hour convergence window.
- **Mailchimp third-party cost (135 KiB) — correction:** originally attributed to Google Tag Manager, but a follow-up check found no GTM container on the site at all (only GA4's `gtag.js`, which is also hosted on the `googletagmanager.com` domain — that's what caused the mix-up). A later recheck (full page load + scroll, live network capture, logged into wp-admin) also found zero Mailchimp/chimp requests, so the original 135 KiB finding didn't reproduce this time. Not chased further; if it recurs, trace it to the actual injecting plugin rather than GTM, and check whether it's a logged-out/first-visit-only trigger.
- **QUIC.cloud CDN session expired mid-session** — declined to enter the account password myself per this project's hard credential rule even when offered; user logged in and purged the CDN cache on their own device, confirmed via `x-qc-cache: miss`.
- Final scores this session (fresh run, both cache layers purged): Performance mobile 59 / desktop 84, Accessibility 97/97 ✅, Best Practices 100/100 ✅, SEO 100/100 ✅. No regressions left live. See [`docs/2026-08-08-performance-follow-up.md`](docs/2026-08-08-performance-follow-up.md).

### Performance (follow-up, continued)
- **QUIC.cloud Critical CSS re-enabled and confirmed working** — unblocked the crawler (course-bundle URLs were mistakenly auto-blocklisted), re-enabled Load CSS Asynchronously with verified coordinate-clicks, confirmed via fresh page load + cache-miss fetch. Render-blocking savings estimate dropped from ~4.1s to ~2.9s while CCSS backfilled. **Left live.**
- **Discovered Imagify's WebP delivery was never actually turned on site-wide** — a real fetch showed 850KB raw PNGs being served despite Imagify reporting ~150KB WebP versions existed on disk; root cause was "Display images in Next-Gen format on the site" being unchecked. Enabling it cut real transfer size by 82% (confirmed), but broke the three course-bundle card images (rendered invisible — loaded but `visibility:hidden`, from a conflict between Imagify's `<picture>` rewrite and LiteSpeed's own lazy-load mechanism). **Reverted** to avoid the live regression; flagged as the single biggest remaining lever (site-wide, not just 3 images) for a future session once the lazy-load conflict is resolved.
- **Course-bundle thumbnail right-sizing: two attempts, both reverted.** Confirmed the cards are rendered by a Tutor LMS shortcode, not editable Elementor widgets. First JS-snippet attempt swapped images post-load (too late — original already fully downloaded, net-negative). Second attempt tried pre-load swapping but the browser had already started fetching before the script ran. Snippet deactivated (not deleted) in WPCode.
- No regressions left live — both real issues found (image swap net-negative; WebP/lazy-load conflict) were caught and reverted before being left on. See [`docs/2026-08-08-performance-follow-up.md`](docs/2026-08-08-performance-follow-up.md).
