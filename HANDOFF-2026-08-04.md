**New root cause found and worked around: TinyMCE leaves a stray
`<span data-mce-type="bookmark">` in saved content when you switch Visual→Code→Visual
with the cursor resting where a `<script type="application/ld+json">` block
follows.** On `/cams-exam-pass-rate/`, editing then toggling tabs left this
literal span injected into the `FAQPage` JSON-LD string value, breaking the
JSON (confirmed via `JSON.parse` throwing on the live page immediately after
publish — caught before this could sit unnoticed). Fixed by locating the
span in the Code-view textarea (`indexOf('<span data-mce-type=\"bookmark\"')`)
and deleting it, then republishing **without** switching back to Visual
(the switch itself seems to be what re-triggers the insertion). Any future
Elementor edit on a page whose Text Editor widget contains a raw
`<script type="application/ld+json">` block should fetch the live page after
publishing and confirm `JSON.parse` succeeds on every JSON-LD script tag —
don't trust the Elementor canvas preview or the "Publish" button going gray
as proof the schema is still valid JSON.

**Confirmed (again) that these Text Editor widgets hold the ENTIRE article
as one Elementor widget**, not one widget per paragraph. `Ctrl+A` inside the
Code-view textarea selects the whole article, not the current paragraph —
typing over that selection deletes everything after the first paragraph.
This was caught before publishing (via `Ctrl+Z` undo) and nothing bad ever
went live, but it's a real trap. The safe pattern that worked cleanly for
every edit this session: read the exact target substring via
`textarea.value.indexOf(...)`, position the cursor with
`textarea.setSelectionRange(start, end)` (a safe, read-only-equivalent DOM
call — it only moves the selection, never touches `.value`), verify
`selectionStart`/`selectionEnd`/the selected text match exactly what you
expect, *then* type the replacement as real keystrokes. Never `Ctrl+A` and
never assign `.value` directly via JS on these widgets.

## The one thing to understand before touching anything else

A full 11-stream SEO audit on 2026-08-03 found that **roughly half of what
prior sessions reported as "done" was never actually live in production.**
This is not a strategy failure — the fixes were the right fixes. It's a
**verification failure**: this site's own admin tooling (WPCode's save
confirmation, Elementor's editor state, LiteSpeed's purge toast, Rank Math's
settings-saved message) is not trustworthy evidence that a change reached the
live HTTP response. The only reliable check is a cold, cache-busted fetch of
the actual production page — `fetch(url, {cache:'no-store', credentials:'omit'})`
or `curl` from outside the browser session — never the wp-admin UI's own
confirmation.

**Before marking anything "done" in a future session: verify it with a fresh
no-cache fetch against the live URL. Every single time. No exceptions.**

## Three confirmed root causes for silent fix failures

### 1. WPCode snippets sometimes silently fail to propagate
Reproduced twice this project: a snippet saves in wp-admin, the editor shows
the new code, but the live response never changes — confirmed via `curl`
(bypassing the browser entirely), even after multiple cache purges. Root
cause not fully isolated. Mitigation: after any WPCode save, toggle the
snippet off → save → on → save again to force clean re-registration, then
verify live. If it still doesn't take, the change needs to go in an actual
`mu-plugins` file instead (loads from disk every request, no save/registration
step to fail) — **blocked**: Theme File Editor is disabled site-wide and no
FTP/SFTP access exists from this session. Needs the user to grant file access
or open a Hostinger support ticket.

### 2. Aggressive multi-layer caching hides whether a fix reached origin
LiteSpeed page cache sat at a 7-day TTL, behind QUIC.cloud's CDN edge.
LiteSpeed's generic "Purge All" does not reliably reach the QUIC.cloud edge
layer — only "Purge By URL" (targeted) does, and even that needs an
independent no-cache fetch to confirm, never the admin UI's "purged" toast.
**Fixed this session:** Default Public Cache TTL and Default Front Page TTL
both dropped from 604800s (7 days) to 86400s (1 day) — LiteSpeed Cache →
[2] TTL tab. Auto-purge-on-publish/update was already well configured (All
pages, Front page, Author archive, Post type archive all checked under
[3] Purge) and was left as-is.

### 3. Elementor stores content in two places that can desync
`post_content` (WordPress-standard, tracked by native revisions) and
`_elementor_data` (Elementor's own postmeta, its actual rendering source of
truth) can drift apart. WordPress's native "Restore Revision" only touches
`post_content` — Elementor's real rendering source is untouched, so a revert
can look successful and then silently un-revert the next time anyone opens
the post in Elementor. Reproduced directly on post 8129 (see below). Checked
Elementor → Tools for a resync/regenerate utility — **none exists** in this
install. The only fixes are direct database access (`wp post meta update` /
phpMyAdmin edit to `_elementor_data`) or a human manually re-authoring the
content live in Elementor's visual editor via real clicks/typing — never
JS-injected value-setting into the textarea, which is what caused this in the
first place.

## Operational gotchas (carried forward + new this session)

1. **LiteSpeed cache purging**: "Purge By URL" (targeted), not "Purge All" —
   confirmed the only method that reliably reaches the QUIC.cloud edge.
   Always verify via a fresh `fetch(url, {cache:'no-store', credentials:'omit'})`
   after purging, never the admin UI's "purged" toast.
2. **WPCode save clicks can silently fail** — verify by hard-reloading the
   snippet edit page and re-reading the actual value, not the in-page state
   right after clicking. A more reliable click method: match buttons by exact
   text via `document.querySelectorAll('button')` + `.click()` in
   `javascript_exec`, rather than a cached element reference.
3. **CodeMirror-style code editors (WPCode's PHP editor) auto-close
   brackets** — typing a full block with explicit closing braces produces
   duplicated closing braces. Either let auto-close handle closing brackets
   (don't type them yourself) or clean up the duplicates before saving.
4. **Text-field `ctrl+a` select-all can leave a stray leading character**
   when immediately followed by typing (timing/event-order issue, seen on
   Rank Math's meta-description textarea). Safer: click into the field,
   triple-click to select the line, or `Home`→`shift+End`→`Delete`, then
   screenshot-check before saving.
5. **Rank Math's Schema Builder "Advanced Editor" (raw JSON view) can hang
   the page** — avoid it. For schema fields not exposed in the normal Schema
   Builder UI, prefer a WPCode output-buffer snippet (once WPCode reliability
   is sorted — see root cause #1) rather than fighting the Advanced Editor.
6. **Screenshot tool has intermittent ~30s timeouts** that are not always a
   real page freeze — try `get_page_text` or a `javascript_exec` check before
   assuming the page is broken.
7. **Theme File Editor is disabled** (`Appearance → Theme File Editor`
   returns "Sorry, you are not allowed to access this page") — no direct
   theme-file access from wp-admin. No FTP/SFTP/hosting-panel credentials
   available to any session so far. This blocks: proper `mu-plugins` fixes,
   direct edits to whatever theme template still emits the orphan-schema
   bug's actual source, and removing the physical robots.txt/llms.txt files.
8. **Elementor JS-value-injection into the Code-view textarea corrupts the
   page** — confirmed twice on post 8129 (the theme's own `<h1>` title
   disappears sitewide on that post, unrelated to what content was actually
   edited). Real-keystroke typing into the *visual* canvas is safer but still
   risky at precise text-selection boundaries — a wrong click merged a
   heading into a paragraph on one attempt this session. Any future edit to
   Elementor-managed content should be done by a human, not automation,
   until this is better understood.
9. **`resize_window` browser tool does not reliably resize the actual
   viewport** — confirmed via direct `window.innerWidth` check staying at
   the original size after calling it. Use Playwright's own viewport-sweep
   capability (via the seo-visual skill/subagent) for responsive testing
   instead of this tool.
10. **Two audit/plan docs vanished from the repo working directory twice** in
    the 07-30/07-31 sessions, restored via `git checkout HEAD -- <file>`.
    Suspected cause: an earlier `/seo audit` subagent's writes to the project
    directory. Not reproduced this session, but if a tracked file goes
    missing unexpectedly, check git history before assuming the content is
    gone — don't recreate from memory.
